# 言い訳コロシアム 要件定義書

## 1. プロジェクト概要

### 背景

生成AIアプリの多くは単発のチャット体験に留まり、ゲーム進行、複数AIエージェント、リアルタイム配信、スコア保存、監視、コスト最適化まで含めた実践的な設計を示しにくい。

本プロジェクトは、AIが生成する理不尽な状況に対してプレイヤーが自由入力で言い訳し、複数のAI審査員が評価・議論するゲームを通じて、生成AIアプリ設計とAWSアーキテクチャ設計をポートフォリオとして示す。

### 目的

- 1人で3〜5分遊べるテキストベースのAI対話型ゲームをMVPとして完成させる。
- Amazon Bedrock、Lambda、DynamoDB、Step Functions、CloudWatchを使ったAWS学習用ポートフォリオを構築する。
- 将来的にAppSync EventsまたはWebSocket、SQS FIFO、EKS GPU上のOSS生成モデルへ拡張できる設計にする。

### 提供価値

- プレイヤーは毎回異なる理不尽な事件に対して、自分の言葉で弁明する即興の言語バトルを楽しめる。
- AI審査員の人格ごとの評価や議論により、回答後の観戦体験も楽しめる。
- 開発者は生成AI、AWSサーバレス、リアルタイム配信、ワークフロー制御、コスト監視を一貫した題材で説明できる。

### 開発規模

- 開発体制: 個人開発
- フェーズ: Phase 1 テキストMVP
- 成果物: アプリ本体、README、アーキテクチャ図、AWS構成説明、将来拡張方針

## 2. ユーザー・ステークホルダー

### プライマリユーザー

- **ペルソナ**: 生成AIや大喜利系ゲームが好きな個人ユーザー
- **利用シーン**: 休憩時間、SNS共有前の短時間プレイ、ポートフォリオデモ視聴時
- **抱えている課題**: 決まった選択肢ではなく、自分の言葉でAIを相手に遊べる軽いゲーム体験が少ない
- **期待価値**: 予測できないお題、笑える評価、もう一度遊びたくなる短時間体験

### セカンダリユーザー

- **採用担当者・面接官**: 生成AIアプリとAWS設計の実装力を短時間で確認したい
- **開発者本人**: AWS、Bedrock、Step Functions、DynamoDB、監視設計の学習成果を説明したい

### ステークホルダー

- プロダクトオーナー: 開発者本人
- 運用者: 開発者本人
- 外部依存先: AWS、Amazon Bedrock、将来フェーズのOSS生成モデル

## 3. ユビキタス言語

| 用語 | 定義 | 使わない言葉 |
| --- | --- | --- |
| 言い訳 | プレイヤーが事件に対して入力する弁明・謝罪・交渉文 | 回答、発言のみ |
| お題 | AIが生成する世界線、事件、プレイヤーの立場、相手キャラクターのセット | 問題、クイズ |
| 世界線 | 事件が起きる舞台設定。現代、SF、ファンタジー、王国など | ステージ |
| 事件 | プレイヤーが弁明すべき失態やトラブル | シナリオ、状況のみ |
| 被告 | お題内で失態を起こしたプレイヤーの立場 | プレイヤーキャラ |
| AI審査員 | プレイヤーの言い訳を観点別に評価するAIキャラクター | 評価AI |
| 審判AI | 最終スコアと判定ランクを出すAI | 最終評価AI |
| 評価軸 | 説得力、面白さ、誠実さ、リスク回避力などの採点観点 | 採点項目 |
| 判定ランク | S〜E、EXなどの最終称号 | グレード |
| プレイログ | お題、言い訳、AIコメント、スコア、判定を含む1プレイの記録 | 会話履歴のみ |

## 4. ドメインモデル

### Entity

- **GameSession**: 1回のプレイを表す。セッションID、状態、開始時刻、終了時刻を持つ。
- **Scenario**: 世界線、事件、被告の立場、怒れる当事者を持つ。
- **PlayerExcuse**: プレイヤーが入力した言い訳本文、入力時刻、文字数を持つ。
- **JudgeComment**: AI審査員ごとの評価コメント、評価軸別スコア、発言順を持つ。
- **FinalJudgement**: 総合スコア、判定ランク、最終コメント、改善ポイントを持つ。
- **PlayLog**: 1プレイの保存用履歴。Scenario、PlayerExcuse、JudgeComment、FinalJudgementを束ねる。

### Value Object

- **Score**: 0〜100点の数値。評価軸別スコアにも使用する。
- **Rank**: S / A / B / C / D / E / EX のいずれか。
- **JudgeRole**: 審判AI、検察官AI、弁護人AI、監査官AI、民衆AIなどの役割。
- **WorldType**: 現代、ファンタジー、SF、異世界、王国、宇宙船、AI都市など。
- **SafetyStatus**: お題や出力が許可、要修正、拒否のどれに該当するか。

### Aggregate

- **GameSession Aggregate**
  - Root: GameSession
  - 含む: Scenario、PlayerExcuse、JudgeComment、FinalJudgement
  - 不変条件:
    - 1つのGameSessionには1つのScenarioのみ紐づく。
    - PlayerExcuseはScenario生成後にのみ登録できる。
    - FinalJudgementは必要なAI審査員コメントが揃った後にのみ生成できる。
    - 完了済みGameSessionのスコアと判定は通常更新しない。

- **PlayLog Aggregate**
  - Root: PlayLog
  - 含む: 保存対象のセッション結果一式
  - 不変条件:
    - 保存済みログは監査・ポートフォリオ説明に使えるよう、主要な生成結果を欠落させない。
    - 不適切コンテンツ判定されたログは公開共有対象にしない。

### 可用性

- MVPの稼働率目標: 99.0%/月
- 障害時はゲーム中断を許容し、エラー内容をユーザーに短く表示する。
- BedrockやLambda失敗時はリトライ回数を制限し、無限実行を避ける。

### スケーラビリティ

| フェーズ | 想定規模 | 方針 |
| --- | --- | --- |
| MVP | 個人利用〜デモ利用、DAU 10〜100 | Lambda、DynamoDB、Bedrock中心 |
| Phase 3 | SNS共有やデモで一時的な同時接続増 | AppSync EventsまたはWebSocket、SQS FIFO |
| Phase 4以降 | 画像・音声生成ジョブ増 | KEDA、Karpenter、EKS GPUを必要時のみ起動 |

### 保守性

- プロンプトテンプレート、評価軸、AI審査員の人格はコードから分離し、変更しやすくする。
- Bedrock呼び出し、スコア計算、ログ保存、UI表示を責務分離する。
- AWSリソースと環境変数はREADMEまたはインフラ定義で説明する。

### データ保持

- MVPではプレイログをDynamoDBに保存する。
- 保存対象は、お題、言い訳、AIコメント、スコア、判定、実行時刻、エラー情報の最小限とする。

## 8. セキュリティ設計

### 認証・認可

- MVP認証方式: 本格的なユーザー認証なし。
- ロール設計: MVPでは一般プレイヤーのみ。
- 管理者画面、ランキング、ユーザー別履歴を追加する場合は、Cognito等による認証と管理者ロールを導入する。

### データ保護

- 通信: HTTPS必須。
- 保存データ: プレイログ、入力文、AI出力、スコアを保存する。
- 個人情報: MVPではメールアドレス、氏名、住所、決済情報を収集しない。
- センシティブデータ: 医療・金融データは扱わない。
- ユーザー入力には不適切表現が含まれる可能性があるため、公開共有やログ閲覧時の取り扱いを制限する。

### AI安全性

- 不適切なお題生成を避けるため、暴力、差別、性的内容、実在個人への中傷、違法行為助長を避けるガードレールを設ける。
- AI審査員のコメントは人格付けを行うが、ユーザー人格への攻撃ではなく、ゲーム内の言い訳への評価に限定する。
- エラー時や安全性チェック失敗時は、別のお題を再生成するか、ユーザーに再試行を促す。

### API・通信防御

- CORS: 許可オリジンを明示的に設定する。`*` は使わない。
- レートリミット: 1ユーザーまたは1 IPあたりのゲーム開始回数に上限を設ける。
- セキュリティヘッダー: CSP、X-Frame-Options、X-Content-Type-Optionsを設定する。
- 入力バリデーション: 言い訳本文の文字数上限、空文字禁止、制御文字除去を行う。
- エラー応答: スタックトレースやAWS内部情報を返さない。

### 秘密情報管理

- AWS認証情報、Bedrock関連設定、APIキーは環境変数またはAWS Secrets Managerで管理する。
- `.env`、アクセスキー、生成シークレットはコミットしない。
- BedrockモデルID、リージョン、コスト上限は設定値として管理する。

### 監査ログ・インシデント対応

- CloudWatchにBedrock呼び出し回数、エラー率、レイテンシ、トークン数相当、概算コストを出す。
- ログ保持期間、データ侵害時の通知方針はTBD。

### コンプライアンス

- MVPで個人情報を収集しない場合、個人情報保護法上の対応は限定的。
- 認証やメールアドレス保存を導入する場合は、プライバシーポリシー、収集目的、削除窓口を用意する。
- GDPR、HIPAA、PCI DSSは現時点では対象外。

## 9. スコープ管理

### やること（Phase 1 MVP）

- テキストベースのお題生成
- プレイヤーの言い訳入力
- AI審査員3名による評価
- 審判AIによる最終判定
- 評価軸別スコアと判定ランクの表示
- プレイログ保存
- CloudWatchログ出力
- GitHub READMEでアーキテクチャと技術選定理由を説明
- Bedrock呼び出し回数、トークン、失敗率、平均応答時間の記録方針
- 不適切なお題生成を避ける最低限のガードレール

### やらないこと（MVPスコープ外）

- 画像生成
- 音声生成、TTS、BGM、SE
- 口パク動画
- 3Dキャラクター
- マルチプレイ
- ランキング
- 課金
- 本格的なユーザー認証
- SNS共有カード生成
- EKS GPU上のOSSモデル実行

### 将来フェーズ

- Phase 2: Step Functionsによるゲーム進行ワークフロー化
- Phase 3: AppSync EventsまたはWebSocket、SQS FIFOによるリアルタイム議論
- Phase 4: EKS GPU、KEDA、Karpenter、OSS生成モデルによるリッチメディア生成
- Phase 5: ランク、称号、ステージ制、審査員セット選択、大喜利モード、ガチ弁明モード、ランキング、共有機能
- Phase 6: デモ動画、コスト試算、監視メトリクス画面、ポートフォリオ整備

### 実装開始時の推奨デフォルト

- MVP審査員: 検察官AI、弁護人AI、民衆AIの3名。

- Step Functions: Phase 2で導入。ただしMVPの処理単位は将来の状態機械に分割しやすく実装する。
- リアルタイム配信: MVPでは疑似的な順次表示で代替し、Phase 3で本実装する。
